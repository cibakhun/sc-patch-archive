<assumption_delta_decision>
**Ausgeloest durch:** Der Preset-Name wird in dieser Phase von einem faktisch festen
Schluessel zu einem aenderbaren Feld (`required/fest` → `wandelbar`). Damit steht die
Identitaetsfrage im Raum: traegt der Name noch die richtige Rolle?

**Primaeres Substantiv:** weiterhin der **Name** — die Identitaet eines Presets ist
`(user_id, name)`, so wie es Migration `20260812040000_mining_sig_presets.sql` Zeile 25
festlegt.

**Entscheidung: `no-change`.** Begruendung: Ein Umbenennen per `UPDATE` auf die
Schluesselspalte ist in Postgres eine normale Operation, die bestehende UPDATE-Politik
ist gegenueber dem Namen blind (sie prueft nur `user_id`), und der einzige Fehlerfall
ist die Eindeutigkeitsverletzung, die diese Phase sichtbar behandelt. Eine
Ersatzschluessel-Spalte (`id`) einzufuehren waere ein Schemaumbau an einer Tabelle mit
echten Nutzerdaten, den CONTEXT.md nirgends verlangt.

**Was ein spaeteres `promote` erzwingen wuerde:** Phase 11 („Geteilte Routen mit
Spielerbewertung"). Sobald ein Preset eine oeffentliche Adresse bekommt, macht jedes
Umbenennen diese Adresse ungueltig — dann braucht es einen stabilen Ersatzschluessel.
Die Migration dafuer waere additiv (Spalte hinzufuegen), nicht zerstoerend; der Preis
ist das Nachziehen jeder Aufrufstelle. Dieser Absatz ist die Uebergabe an Phase 11.
</assumption_delta_decision>
