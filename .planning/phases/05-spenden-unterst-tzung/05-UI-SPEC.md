# Phase 5 — UI Design Contract: Spenden-Unterstützung ("Unterstützen")

> Visual and interaction contract for `/support.html` + `/de/support.html`, the three
> site-wide entry points (footer, menu, tool-page strip), and the operator moderation
> surface. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **This is NOT a greenfield page.** VerseBase has a strong, established visual
> language (per-page dark palette + generated light twin, fluid `clamp()` type scale,
> `assets/theme.css` effect tokens, `FeedbackForm.astro`-style shared components). This
> contract extends that language; it does not replace it. Every table below cites the
> existing file/value it derives from wherever one exists.

## Spacing Scale

New component prefix for this phase: **`spt-`** (Support). Verified unused (`grep -r "\.spt-" src` → 0 matches). Per `CONVENTIONS.md` § Naming Patterns: "new page = new prefix."

Declared values for all new `spt-*` component-internal spacing (multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | icon-to-label gaps, badge internal padding |
| sm | 8px | pill/chip internal gaps, checkbox-to-label gap (matches `.fbx-stars` `gap:0.2rem`≈3.6px rounded up to the 4px grid for new work) |
| md | 16px | field-to-field gaps in the amount picker and message field, wall card internal padding |
| lg | 24px | card padding (`.spt-card`), wall grid row gap |
| xl | 32px | gap between page body sections (reason → amount picker → progress → wall) |
| 2xl | 48px | hero-to-first-section transition |
| 3xl | 64px | page-level breathing room (hero bottom padding, footer-adjacent spacing) |

**Exceptions (cited, not invented):**
- Hero and section-wrapper **horizontal** padding uses the site's existing fluid pattern, not a fixed px value: `padding: 0 clamp(1.25rem, 5vw, 4rem)`, identical to `feedback.astro` `.fbwrap` / `.sec-head`. This is intentional site-wide chrome consistency, not a violation of the 4px grid — it governs viewport-responsive gutters, not component-internal spacing.
- Icon-only controls and any element that must remain visually small (amount-preset pills at their tightest breakpoint, wall card badge) get a 44px **hit target** via a transparent `::after`, per the established `mobile-ux.css` §2/§3 technique — the drawn box stays small, only the tappable area grows. **New `spt-*` targets falling under 44px on ≤820px MUST be added to `mobile-ux.css`'s named-selector lists** (§2 for buttons/controls, §2b for link rows) — do not invent a parallel mechanism.

## Typography

The site does not use a fixed px scale — it uses fluid `clamp()` tied to viewport width, consistently across every hero/section on the site. The support page follows the exact same convention (cited, not new):

| Role | Size | Weight | Line Height | Source |
|------|------|--------|-------------|--------|
| Body | `1rem` (18px) | 400 | 1.5 | `.fbx-input`/`.fbx-textarea` (`FeedbackForm.astro`) |
| Label (UI caps) | `0.82rem` (14.8px), uppercase, `letter-spacing: 0.1em` | 700 | 1 | `.fbx-label` (`FeedbackForm.astro`) |
| Heading (section, `.sec-head h2`) | `clamp(1.5rem, 3.5vw, 2.4rem)` → 27–43px | 700 | 1.05 | `assets/detail.css:63` |
| Display (hero `h1`) | `clamp(2.4rem, 12vw, 9rem)` → 43–162px; the `.thin` eyebrow sub-line inside it is `.34em` of that, weight 500 | 900 (sub-line 500) | 0.86 | `assets/detail.css:103,105` |

**Weights in use: 400 (body), 500 (hero `.thin` sub-line only), 700 (labels/headings/CTA), 900 (hero display only).** This is 4 nominal weights, exceeding the template's "2 weights max" guidance — flagged deliberately as an *existing site-wide convention being reused verbatim*, not a new invention for this phase. The hero's 900/500 pairing is load-bearing for MOTN-02 (exactly one visible `h1`) across the whole site; introducing a different weight pair only for `/support.html` would itself be the inconsistency.

## Color

### The fixed "Unterstützen" gold token (D-09)

This is the one color on the entire site that does **not** come from the current page's own palette. It must be recognizable identically on a blue archive page, an amber feedback page, a green mining page, etc. — because it marks the SAME feature (footer line, menu entry, tool-page strip) wherever it appears.

**Declared in `assets/theme.css`** (not in any `.astro` inline `<style>`), as a fourth, phase-5-specific block appended after the existing three (base/effect/media tokens), keeping the file's own "no layout rules, only color" contract:

```css
/* ============================================================
   4 — SUPPORT-GOLD (Phase 5, D-09)
   Eigene, feste Farbe für den Spenden-Zugang — unabhängig von der
   Palette der jeweiligen Seite. Bewusster Bruch mit „jede Seite ihre
   eigene Farbwelt" zugunsten der Wiedererkennbarkeit (drei Zugänge:
   Fuß-Zeile, Menü-Eintrag, Werkzeugseiten-Streifen).
   ACHTUNG: diese Datei ist ein PLAIN Stylesheet, kein .astro mit
   inline <style> — der Hellmodus-Generator (npm run theme) sieht sie
   NICHT. Der Hellwert unten ist darum von Hand gesetzt und bleibt es;
   „npm run theme" nach einer Änderung hier zu laufen lassen ändert
   nichts an diesem Block und ist kein Fehler.
   ============================================================ */
:root {
  --support-gold: #e8a83c;
  --support-gold-ink: #1a1004;      /* Text/Icon AUF einer --support-gold-Fläche */
  --support-gold-soft: color-mix(in srgb, var(--support-gold) 14%, transparent);
}
:root[data-theme='light'] {
  --support-gold: #7a4e05;
  --support-gold-ink: #ffffff;      /* deckt sich mit --ink im Hellmodus */
  --support-gold-soft: color-mix(in srgb, var(--support-gold) 10%, transparent);
}
```

**Measured contrast (WCAG relative-luminance formula, both clear AA):**

| Pair | Ratio | Against |
|------|-------|---------|
| `#e8a83c` (dark token) on `#1b2230` (a representative dark page surface, `FxToggle.astro` `--surface-2` fallback) | **7.7 : 1** | text-on-surface, AA 4.5:1 |
| `#1a1004` (dark ink) on `#e8a83c` (dark token, filled button/badge) | **10.1 : 1** | text-on-accent |
| `#7a4e05` (light token) on `#f5ece3` (feedback.astro's own generated light `--bg-2` — the worst-case light amber surface it will sit near) | **6.2 : 1** | text-on-surface |
| `#7a4e05` (light token) on `#e9ecf4` (theme.css's default light `--bg-2` fallback, cooler tone) | **6.1 : 1** | text-on-surface |
| `#ffffff` (light ink) on `#7a4e05` (light token, filled button/badge) | **7.2 : 1** | text-on-accent |

All four exceed 4.5:1 (text) comfortably and are nowhere near the 3:1 floor for large text/UI boundaries. Against the SiteNav menu's fixed `--chrome-panel` surface (`rgba(6,10,20,.92)` dark / `rgba(253,253,255,.96)` light) contrast is higher still, since that surface is closer to pure black/white than either measured case above.

**Where `--support-gold` is used (reserved-for list — exhaustive):**
- Primary CTA button fill on `/support.html` (`.spt-cta`)
- Progress bar fill (`.spt-bar__fill`)
- Supporter-wall linked-profile badge accent (`.spt-wall__badge`)
- The footer line's icon + hover state (`.site-attr .attr-support`)
- The SiteNav menu-overlay row for "Unterstützen" — its icon color and `current`/hover accent, overriding the row's normal inherited page-accent (`.snav-deck__row--support`)
- The tool-page strip's border-accent and CTA (`.spt-strip`)
- The "goal reached" checkmark badge

**Not used for:** general links, focus rings, or borders elsewhere on `/support.html` — those continue to use the page's own `--accent` (see below), which is deliberately set to the *same* hex as `--support-gold` for visual continuity on this one page, without coupling the two mechanisms.

### `/support.html`'s own page palette

Per the per-page-palette rule (`CONVENTIONS.md` § Styling & Theme Rules), the page still carries its own inline dark `:root{}` (its identity, sibling of `feedback.astro`'s amber) followed by a **generated** light twin. Its `--accent` is deliberately the literal dark-token hex so the page's own borders/focus rings/links read as part of the same gold family without importing a CSS variable into a block the generator tokenizes as literal color values:

```css
:root{--bg:#120b05;--bg-2:#1a1108;--surface:#1f1509;--surface-2:#291b0d;--accent:#e8a83c;--accent-2:#ffcf7a;--hot:#e8a83c;--text:#f5ecdc;--muted:#b9a88c;--line:rgba(232,168,60,.20);--line-soft:rgba(245,236,220,.10);--glow:0 0 46px rgba(232,168,60,.24);--ink:#140d05;--maxw:1180px;}
/* Hellmodus — erzeugt von scripts/build-light-palettes.mjs. Nicht von Hand ändern. */
:root[data-theme="light"]{ … läuft aus `npm run theme` … }
```

Run `npm run theme` after adding this block — do not hand-write the light twin (this is the standard per-page rule; it is separate from the hand-written `--support-gold` light value in `theme.css` above, which is a different file under a different rule).

| Secondary (30%) | `var(--surface)` `#1f1509`, `var(--surface-2)` `#291b0d` / light generated | amount-picker card, wall cards, moderation cards |

### 1. `/support.html` page layout (reading order)

Thin-wrapper pattern identical to `feedback.astro`/`FeedbackForm.astro`: `src/pages/support.astro` (EN) + `src/pages/de/support.astro` (DE), both mounting a shared `src/components/SupportForm.astro` (`lang` prop, `COPY` object in frontmatter — direct copy of the `FeedbackForm.astro` shape). `Attribution` + `assets/detail.js` + `assets/detail.css` are pulled in exactly like `feedback.astro`.

1. **Hero** (`.hero`, reused site pattern: `hero__photo` + `#stars` canvas + `hero__in`) — eyebrow "VerseBase · Support", `h1` "Unterstützen"/"Support" with a `.thin` sub-line stating the reason in one clause (see Copywriting Contract "Reason"), no `<canvas>` particle unless the site-wide FX toggle is on (FX-03/FX-04 — this page adds no exception).
2. **Reason section** (`01`, `.sec-head` + prose) — the literal PSU sentence, verbatim, no marketing rewrite (D-11). One paragraph, ≤3 sentences. The no-receipt honesty note (D-21) sits directly under it as a smaller, muted aside — not hidden in fine print, but visually secondary to the reason.
3. **Amount picker** (`02`) — see § 3 below. Stripe Checkout is the primary path; the Ko-fi line sits as the LAST element inside this card, visually subordinate (D-02): smaller type, no button chrome, just a text link with an arrow.
4. **Progress** (`03`) — see § 4. Renders directly under the amount picker, before the wall — a supporter should see "how close" before seeing "who else" and be reassured by the closeness before scrolling further.
5. **Supporter wall** (`04`) — see § 5.
6. Standard `<Attribution>` footer.

At 360px: hero collapses to the standard site hero behavior (already proven at MARK-07/580px monogram breakpoint — no support-specific change needed there), the amount-picker's 4 preset pills wrap to a 2×2 grid (see § 3), the wall's card grid becomes single-column.

### 2. The demo-mode page (D-05/D-15/D-09 combined)

Without Stripe/Ko-fi keys configured (`SUPPORT_DEMO` constant, same shape as `FEEDBACK_DEMO` in `src/consts.ts`):
- A `.spt-demo` banner (identical construction to `.fbx-demo`) sits at the top of the amount-picker card with the "Demo-mode notice" copy.
- The progress bar section (§4) is **entirely absent** from the DOM — not rendered empty, not rendered at 0% (D-15). The reason section and amount picker still render and are still fully interactive (the button shows the demo confirmation panel on click, exactly like `FeedbackForm`'s `showDone()` flow, reusing `.fbx-done`-equivalent `.spt-done`).
- The Ko-fi line is **entirely absent** while no Ko-fi handle is configured (separate flag from the Stripe demo flag — see D-05: "Ko-fi bleibt ausgeblendet, solange kein Name hinterlegt ist").
- The supporter wall still renders (it reads real historical rows if any exist independent of the demo flag; if the table is empty, the "empty wall" copy applies, per DON-09's promise to never fabricate).

### 3. Amount picker — interaction contract

Structure (`.spt-amounts`): one `role="radiogroup"` of 4 preset pills (3 €, 5 €, 10 €, 25 €) + a 5th pill that is a **free-input text field styled as a pill**, all sharing the same visual family; below that, a **second, separate** `role="radiogroup"` of exactly 2 pills for billing frequency (Einmalig/One-time, Monatlich/Monthly).

- **Native-radio-under-styled-label technique**, reused verbatim from `.fbx-star` (`FeedbackForm.astro`): a visually-hidden `<input type="radio">` per pill, the pill itself is the `<label>`, so keyboard Tab/Arrow behavior and screen-reader semantics come from the browser's native radiogroup handling, not custom JS. The free-input pill contains a real `<input type="text" inputmode="decimal">` inside its own `<label>`; selecting it (focus OR typing) sets a 5th hidden radio to "custom" via a `change`/`input` listener (same delegation style already used in `FeedbackForm.astro`'s star-rating script).
- **Preselection (D-03/D-04):** 5 € pill checked by default; "Einmalig"/"One-time" checked by default.
- **Focus order:** amount pills (native radiogroup: one Tab stop, Arrow keys move within) → free-input field → frequency pills (second radiogroup, one Tab stop) → message field (optional) → consent checkbox (optional) → primary CTA button → Ko-fi line.
- **Primary button label updates live** with the current amount + frequency selection (see Copywriting Contract rows) — implemented the same way `FeedbackForm.astro` keeps `#fbRateOut` in sync with star selection: a plain `change` listener, no framework.
- **Min/max handling:** free-input accepts `1`–`500` (integer euros; Stripe's own EUR minimum is €0.50, so 1€ has headroom). Values outside that range do not block typing but **do** block submission and show the "Invalid-amount error" row (`role="alert"`, same `.fbx-status` construction) with focus returned to the field — identical UX to `FeedbackForm.astro`'s `errShort` short-message guard. The server-side check (DON-06) is the actual authority; this is the honest client-side UX layer in front of it, not a substitute for it.
- **Keyboard:** fully operable without a mouse — native radiogroups (arrow keys + Tab), native text input, native checkbox, native submit. No custom keyboard handling needs to be written beyond what `FeedbackForm.astro` already demonstrates.
- **360px:** the 4 preset pills + free-input pill wrap into a 2-column grid (5 pills → 2×2 + 1 full-width free-input row); the frequency toggle stays 2-up (it's exactly 2 options, always fits).

### 4. Progress bar — visual + state contract

`.spt-bar` — a horizontal bar, not a circular gauge (matches the SiteNav scroll-progress bar's horizontal language already on every page, `.snav__progress-bar`, so the motif isn't invented fresh).

- **States:**
  1. **Demo/no data → absent.** No DOM node rendered at all (see § 2). This IS the resolution for DON-09/D-15 — there is no "empty bar" visual to design because it must not exist.
  2. **In progress.** Fill width = `min(100, round(sumCents / goalCents * 100))%`, label "€X of €120" reads the literal summed value, never an estimate.
  3. **Goal reached (D-14).** Fill sits visibly at 100%; a checkmark badge (using `--support-gold-ink` on `--support-gold`, same visual language as `.fbx-done__mark`) appears at the bar's end; the "Goal-reached heading/body" copy replaces the amount-picker's framing copy ABOVE it (the picker itself stays functional and visible — D-14: "der Weg bleibt offen, wird aber nicht mehr eingefordert" — it just loses its urgency framing, not its function).
- **Screen readers:** the bar carries `role="progressbar"` `aria-valuenow`/`aria-valuemin="0"`/`aria-valuemax="120"` and `aria-valuetext="€35 of €120"` (the literal label, not just the number) so assistive tech announces the same honest sentence a sighted user reads. ### 8. Focus, keyboard, screen-reader, reduced-motion contract (cross-cutting)

- **Focus ring:** `outline: 2px solid var(--accent); outline-offset: 3px` on `:focus-visible`, exactly as `.fxsw:focus-visible` / `.fbx-input:focus`. New `spt-*` interactive elements must not invent a different focus treatment.
- **All new interactive elements are native HTML controls** (`<input type="radio">`, `<input type="text">`, `<input type="checkbox">`, `<button>`, `<a>`) — no custom-widget ARIA (`role="button"` on a `<div>`, etc.) is needed anywhere in this phase; every interaction pattern above maps to something `FeedbackForm.astro` already does with plain form elements.
- **Live regions:** amount-error and moderation-action-error both use `role="alert"` + `aria-live="assertive"` (matches `.fbx-status`); the progress bar uses `aria-live="polite"` implicitly via its `role="progressbar"` `aria-valuetext` (a value-text change on a progressbar role is announced by AT without an explicit `aria-live`, so none is added — adding one would double-announce).
- **Reduced motion:** progress-bar fill transition, any hero canvas/particle motion (governed entirely by the existing FX-01…FX-08 contract from Phase 1.1 — this phase adds NO new ambient motion), and any card-reveal animation on the wall all sit behind the site's standard `@media (prefers-reduced-motion: reduce)` block. Nothing in this phase may be a precondition for operability under reduced motion (house rule 6) — every state described above (selected pill, filled bar, revealed card) has a static, immediately-correct rendering with motion removed.
