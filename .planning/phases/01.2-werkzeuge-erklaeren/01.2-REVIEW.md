# Phase 01.2: Code Review Report

**Reviewed:** 2026-08-06
**Depth:** deep (import graph: `help.ts` → `ToolHelp.astro` → 11 wiring sites; runtime: `tool-help.js` against the other 9 document-level `keydown`/`Escape` handlers and the client renderers `item-finder-app.js`, `crafting-app.js`, `RefineryDashboard`'s inline script)
**Files Reviewed:** 16
**Status:** issues_found

## Summary

Stage 1 (the `<details>` purpose section, the catalog and its parity assertion) is solid work.
`assertHelpParity()` is a genuinely good gate, `useHelp()` is only ever reachable from `.astro`
frontmatter so its throw can only break the build (never a page), and the `vb.help.seen` reader
handles `null`, non-JSON, arrays and a throwing `localStorage` correctly.

Stage 2 is where the defects are, and they cluster in one place: **`onPoint()` (`assets/tool-help.js:141-155`)
is a show-only handler with no hide path, no viewport clamping and no pointer-transparency.** Three
consequences of that single function are Critical: the bubble is invisible on the tall anchors
(`#wk-tc-grid`, `details.pj-tbl[open]`, `#rfd-history`), it physically blocks the controls it sits on
top of, and its `aria-describedby` lands on the wrapper `<div>` rather than on the element the
keyboard user actually focused — so screen readers announce nothing at all for most anchors.

Second theme: the first-visit marker is burned for sections that are **provably invisible at the moment
it is written** (Item Finder below 901 px, Refinery Tracker while logged out). D-09 is defeated for
exactly those visitors.

Third theme: `verify-help.mjs` is honest about what it checks, but it cannot see whether Stage 2 has any
anchors at all — a tool that loses every `data-help` still reports "11 von 11".

**Suspicions that did not survive checking, and are deliberately not listed below:** no listener leak
across on/off cycles (`onPoint`/`onEscape` are stable references and `removeEventListener` matches);
`window.__toolHelpLoaded` really does stop the second execution on `/topics/mining.html`, where two
ToolHelp instances emit the script twice; no double CSS injection is reachable (`activate()` is only
called after `deactivate()`); `data-help` really does sit on the stable wrappers that
`item-finder-app.js:226/251/287/311` re-fill via `innerHTML`, so DOC-03 holds; no focus trap exists;
no `data-help` element carries a pre-existing `aria-describedby` that could be destroyed; the bubble
does inherit the page palette (page CSS defines `--accent`/`--surface`/`--text` on `:root`), so the
Stage-2 CSS fallbacks are cosmetic-only; and a scan of all 252 new user-visible strings found **no**
data-provenance leak (no Data.p4k / DataCore / datamined / scmdb reference).

## Critical Issues

### CR-01: The explanation bubble is placed below the *whole* anchor and is off-screen for tall anchors

**File:** `assets/tool-help.js:148-150`
**Issue:** The bubble is positioned at `rect.bottom + 8` of the matched `[data-help]` element with no
viewport clamping and no flip. Several anchors are whole containers that are many viewport heights tall,
so the bubble is drawn far below the fold and the visitor sees an outline with no explanation.

**Failure scenario:**
`/topics/wikelo-emporium.html` → open the help section → press "Elemente erklären" → hover any trade card.
`e.target.closest('[data-help]')` walks up to `div#wk-tc-grid` (`src/components/topics/wikelo-emporium.astro:306`),
which contains **every** trade article with its image — several thousand pixels tall. `rect.bottom` is
therefore ~3000+, `bubbleEl.style.top` becomes `3008px` on a `position:fixed` element → the bubble is
rendered outside the viewport. `showPopover()` succeeds, so no error is thrown and nothing hints that
the explanation exists. Identical on `/precision-jump.html` for `details.pj-tbl[open]`
(`PrecisionJumpApp.astro:392`, an open table of all Halo bands), and on `/refinery.html` for
`#rfd-history` / `#rfd-active` once a few orders exist. The same happens for *any* anchor whose bottom
edge is in the lower half of the viewport — e.g. the sort dropdown at the bottom of the Missions filter bar.

**Fix:**
```js
function place(el) {
  var r = el.getBoundingClientRect();
  var bw = bubbleEl.offsetWidth, bh = bubbleEl.offsetHeight;
  var vw = document.documentElement.clientWidth, vh = document.documentElement.clientHeight;
  // Anker ist der SICHTBARE Teil des Elements, nicht sein volles Kastenmass.
  var anchorTop = Math.max(8, r.top);
  var anchorBottom = Math.min(vh - 8, r.bottom);
  var top = anchorBottom + 8;
  if (top + bh > vh - 8) top = Math.max(8, anchorTop - bh - 8);   // nach oben klappen
  bubbleEl.style.top = Math.min(top, vh - bh - 8) + 'px';
  bubbleEl.style.left = Math.min(Math.max(8, r.left), vw - bw - 8) + 'px';
}
```

### CR-02: The bubble sits in the top layer with hit-testing on and never hides — it blocks the controls it explains

**File:** `assets/tool-help.js:85-92` (no `pointer-events`), `assets/tool-help.js:141-155` (no hide path)
**Issue:** `#tool-help__bubble` is a `popover="auto"` element (top layer, above everything) with no
`pointer-events:none`, and `onPoint` only ever *shows* it — there is no `mouseout`, `focusout` or
timer that hides it again. It therefore stays parked over whatever is 8 px below the last anchor and
swallows both hover and click on that area. Turning the help on partially disables the tool it explains.

**Failure scenario:**
`/item-finder.html` (desktop) → help on → hover `#uif-kind-chips`. The bubble is drawn 8 px below that
chip group, i.e. directly over the `<h3>Größe</h3>` heading and the top of `#uif-size-chips`
(`ItemFinderApp.astro:94-96`, a vertically stacked sidebar). Move the mouse down to click a size chip:
the pointer enters the popover instead, so (a) `mouseover` never reaches `#uif-size-chips` and its
explanation can never be shown, and (b) the `mousedown` lands on the popover — it is *inside* the
popover, so it does not even light-dismiss — and the size filter is simply unclickable until the user
clicks somewhere else on the page first. On mobile every tool's toolbar stacks, so this hits every tool.

**Fix:** make the bubble inert to the pointer and give it a hide path:
```js
// in STAGE2_CSS
'#tool-help__bubble{pointer-events:none;position:fixed;…}'

// neu, in activate():
document.addEventListener('mouseout', onLeave);
document.addEventListener('focusout', onLeave);

function onLeave(e) {
  var from = e.target && e.target.closest ? e.target.closest('[data-help]') : null;
  var to = e.relatedTarget && e.relatedTarget.closest ? e.relatedTarget.closest('[data-help]') : null;
  if (!from || from === to || !bubbleEl) return;
  from.removeAttribute('aria-describedby');
  try { bubbleEl.hidePopover(); } catch (err) {}
}
```
(and the matching `removeEventListener` pair in `deactivate()`).

### CR-03: `aria-describedby` is attached to the wrapper, not to the element that received focus — screen readers announce nothing

**File:** `assets/tool-help.js:142`, `assets/tool-help.js:146`
**Issue:** `onPoint` resolves `el = e.target.closest('[data-help]')` and then sets
`el.setAttribute('aria-describedby', …)`. For the majority of anchors the `[data-help]` element is a
non-focusable wrapper `<div>` and the focused element is a descendant. The description is therefore
attached to a node the assistive technology is not on, and the focused control gets no accessible
description at all. Stage 2 is, for those anchors, purely visual — which contradicts DOC-05
("per Tastatur zu öffnen, zu durchlaufen").

**Failure scenario:**
`/missionen.html` with NVDA → help on → Tab to the "Auftraggeber" dropdown. `focusin` fires with
`e.target = <select>`; `closest('[data-help]')` returns the wrapping `div.mx__f`
(`MissionsApp.astro:132`); `aria-describedby="tool-help__bubble"` is written onto that div. The
`<select>` itself has no `aria-describedby`, so NVDA announces only its label — the explanation is
never spoken. The same applies to `.uif-search` (`ItemFinderApp.astro:79`), `.cdb-search-wrap`
(`CraftingApp.astro:228`), `.mdb-search-wrap` (`MiningApp.astro:111`), `.cbar__search`
(`PatchArchive.astro:172`), `.rfd-dur` (`RefineryDashboard.astro:174`), all five `.mx__f` blocks,
both `.cdb-fgroup`/`.mdb-fgroup` groups and every `.uif-*-chips` group. Only the handful of anchors
written directly onto the control (`#rff-search`, `#sf-*`, `#rfd-station`, `#rfd-method`) work.

**Fix:** describe the element the user is actually on, and clean up afterwards:
```js
function onPoint(e) {
  var el = e.target && e.target.closest ? e.target.closest('[data-help]') : null;
  if (!el || !bubbleEl) return;
  bubbleEl.querySelector('.tool-help__bubble-text').textContent = el.getAttribute('data-help') || '';
  // Beschreibung an den TATSAECHLICH fokussierten Knoten, nicht an die Huelle.
  var describe = (e.type === 'focusin' && e.target.nodeType === 1) ? e.target : el;
  describe.setAttribute('aria-describedby', bubbleEl.id);
  …
}
```
and in `deactivate()`:
```js
var stale = document.querySelectorAll('[aria-describedby="tool-help__bubble"]');
for (var i = 0; i < stale.length; i++) stale[i].removeAttribute('aria-describedby');
```

## Warnings

### WR-01: The first-visit marker is written for sections that are invisible at that moment — D-09 is defeated on mobile and for logged-out tracker visitors

**File:** `assets/tool-help.js:53-70`, `src/components/ItemFinderApp.astro:88-92`, `src/components/account/RefineryDashboard.astro:121,128`
**Issue:** `openOnFirstVisit()` opens every `details.tool-help` it finds and immediately writes
`seen[id] = 1`, without checking whether the section is rendered at all. Two of the eleven sections
are provably not rendered at that instant.

**Failure scenario A (mobile Item Finder):** `.uif-filters` is `display:none` below 901 px until the
visitor ticks `#uif-filters-toggle` (`ItemFinderApp.astro:828-830`). A first-time mobile visitor loads
`/item-finder.html`: the `defer`red script opens the `<details>` inside a `display:none` container and
writes `vb.help.seen.itemfinder = 1`. The visitor never sees the help; on every later visit the section
starts collapsed. The intent of D-09 ("beim ersten Besuch offen") is never delivered to mobile at all.

**Failure scenario B (Refinery Tracker):** `ToolHelp` sits inside `div#rfd[hidden]`
(`RefineryDashboard.astro:121,128`) and the page redirects logged-out visitors to
`/account/login.html`. A logged-out visitor hits `/refinery.html`, the marker is written during the
redirect, and after signing up their genuine first visit shows a collapsed section. (Plan 05 flagged
this as "Annahme A4" for human review — the mobile Item Finder case, which is much larger in traffic,
was not flagged at all.)

**Fix:** only mark seen what was actually shown:
```js
if (id && !seen[id] && section.offsetParent !== null) {   // nicht display:none, nicht in [hidden]
  section.open = true;
  seen[id] = 1;
  changed = true;
}
```

### WR-02: `deactivate()` leaves dangling `aria-describedby` attributes pointing at a removed node

**File:** `assets/tool-help.js:146` (set), `assets/tool-help.js:119-139` (never unset)
**Issue:** `onPoint` writes `aria-describedby="tool-help__bubble"` onto every anchor the visitor ever
touches, and neither `onPoint`, nor `onEscape`, nor `deactivate()` ever removes it. `deactivate()`
removes the bubble node itself (`bubbleEl.remove()`), so the attributes now reference an id that does
not exist for the remaining lifetime of the page.

**Failure scenario:** help on → hover six controls → Esc. The six wrappers keep
`aria-describedby="tool-help__bubble"`; the target element is gone. Screen readers treat a broken
`aria-describedby` reference as a markup error (axe-core rule `aria-valid-attr-value` flags it), and
`npm run audit:site` currently has 4 pre-existing a11y warnings — this one is invisible to it because
it only exists after a runtime interaction.

**Fix:** the `deactivate()` cleanup loop shown under CR-03, plus removal on `mouseout`/`focusout` (CR-02).

### WR-03: Esc collides with every other document-level Esc handler on the same page

**File:** `assets/tool-help.js:116,157-163`
**Issue:** `onEscape` reacts to *any* Escape while help mode is active, without checking
`e.defaultPrevented` or whether something else on the page owns the keypress. Nine other components
already bind `Escape` on `document`, and none of them call `stopPropagation()`.

**Failure scenario:**
- `/item-finder.html`: help on → click an item card → detail modal opens → press Esc to close the
  modal. `assets/item-finder-app.js:959` closes the modal (unconditionally) **and**
  `tool-help.js:158` turns the help off. The visitor loses all outlines as a side effect of closing a modal.
- `/archiv.html`: help on → type in the search field → Esc to clear it. `assets/archive.js:253`
  clears the query **and** the help mode dies.
- `/topics/mining.html` (mobile): help on → open the off-canvas filter drawer → Esc.
  `assets/offcanvas.js:72` closes the drawer **and** the help mode dies.
- Additionally, because the bubble is `popover="auto"`, the browser natively light-dismisses it on the
  same keypress. One Esc therefore performs up to three actions.

**Fix:** make Esc a layered dismissal and yield to whoever already handled it:
```js
function onEscape(e) {
  if (e.key !== 'Escape' || !activeBtn || e.defaultPrevented) return;
  // Erst die Blase, dann der Modus — zwei Druecke, wie ueberall sonst auf der Seite.
  if (bubbleEl && bubbleEl.matches(':popover-open')) { try { bubbleEl.hidePopover(); } catch (err) {} return; }
  setBtnState(activeBtn, false);
  deactivate();
  activeBtn = null;
}
```

### WR-04: No fallback where the Popover API is missing — an empty bubble appears and can never be hidden

**File:** `assets/tool-help.js:85-92,102-112,127-131,152-154`
**Issue:** The bubble relies entirely on the UA stylesheet rule `[popover]:not(:popover-open){display:none}`
to stay hidden. The injected CSS sets no `display` of its own. In a browser that does not implement
the Popover API, the `popover` attribute is inert, there is no UA rule, and `showPopover`/`hidePopover`
throw into empty `catch` blocks (`:130`, `:154`) — the failure is completely silent.

**Failure scenario:** Safari < 17, Firefox < 114, or an older Android WebView. The visitor presses
"Elemente erklären": `activate()` appends the bubble to `<body>` with an empty text span and **no**
`left`/`top` yet, so a `position:fixed` box with `auto` offsets renders as a small empty bordered
rectangle at the bubble's static position — visible immediately, containing only the orange
"Erklärung" eyebrow. `hidePopover()` throws, so it never goes away until the visitor turns the help
off again.

**Fix:** feature-detect and fall back to the `hidden` attribute:
```js
var HAS_POPOVER = typeof HTMLElement !== 'undefined' && 'showPopover' in HTMLElement.prototype;
if (HAS_POPOVER) bubbleEl.setAttribute('popover', 'auto'); else bubbleEl.hidden = true;
// show:  HAS_POPOVER ? bubbleEl.showPopover() : (bubbleEl.hidden = false);
// hide:  HAS_POPOVER ? bubbleEl.hidePopover() : (bubbleEl.hidden = true);
```

### WR-05: `verify-help.mjs` reports "11 von 11" even if Stage 2 has no anchors at all

**File:** `scripts/verify-help.mjs:189-206` (assertion 4), `scripts/verify-help.mjs:154-186` (assertion 3)
**Issue:** Assertion 4 — the one that gates the phase — collects only `data-tool-id` values. Assertion 3
compares `data-help=` counts **between EN and DE**, so `0 === 0` passes. Nothing anywhere asserts that a
page carrying a `data-tool-id` also carries at least one `data-help`, or that any `data-help` value is
non-empty. The gate proves the *purpose section* exists, not that the *element help* does — yet it is
the instance that DOC-01..DOC-07 were checked off against (`REQUIREMENTS.md:85`).

**Failure scenario:** delete every `data-help` attribute from `ShipsOverview.astro:342-382` and rebuild.
`/schiffe.html` and `/de/schiffe.html` both drop to 0 anchors → assertion 3 sees `0 === 0` (pass),
assertion 4 still finds `data-tool-id="ships"` → `--complete` prints
"Abgedeckt: 11 von 11" and exits 0. Pressing "Elemente erklären" on that page then outlines nothing.
The same false negative covers a refactor that renames a toolbar class and drops the attributes with it.

**Fix:** add a sixth assertion, or extend assertion 4:
```js
const helpRe = /data-help="([^"]*)"/g;
for (const f of htmlFiles) {
  const html = htmlCache.get(f);
  if (!html.includes('data-tool-id=')) continue;
  const vals = [...html.matchAll(helpRe)].map((m) => m[1]);
  if (!vals.length) fail(`${f}: data-tool-id vorhanden, aber KEIN data-help-Anker`);
  if (vals.some((v) => !v.trim())) fail(`${f}: leerer data-help-Wert`);
}
```

### WR-06: Thirteen anchors share one content-free sentence

**File:** `src/components/ships/ShipsOverview.astro:343,347,351,355,359,363,368,379`; `src/components/MissionsApp.astro:128,132,136,140,144`; catalog at `src/i18n/help.ts:161,287`
**Issue:** `ships.ctl.select` is reused on eight different dropdowns and `missions.ctl.select` on five,
all saying only "Schränkt die Liste auf einen Wert dieser Auswahlliste ein." / "Narrows the list down
to a value from this dropdown." That is a restatement of what a `<select>` is, not an explanation of
what the control does. D-03 licenses one text per *kind* of control — but "dropdown" is a widget type,
and these eight filter by eight unrelated concepts.

**Failure scenario:** `/schiffe.html` → help on → hover `#sf-sig` ("Signatur") — by far the least
self-evident filter on the page, and the one whose whole point (finding the Prowler as a stealth
freighter) needs explaining. The visitor is told "this dropdown narrows the fleet down to a value".
`#sf-compsize` ("Mindestgröße des Bauteils", disabled until a component is chosen) gets the same
sentence and never explains *why* it is greyed out. Net effect: the two controls that most needed
DOC-02 are the two it helps least.

**Fix:** split at least the non-obvious ones into their own keys — `ships.ctl.sig`, `ships.ctl.comp`,
`ships.ctl.compsize`, `ships.ctl.career`, `missions.ctl.guild` — keeping `ctl.select` for the genuinely
self-describing ones (Hersteller, Größe).

### WR-07: Four Refinery-Tracker anchors collapse to zero height for a new account, and the visible empty-state cards carry no help

**File:** `src/components/account/RefineryDashboard.astro:131,135,167,208` (and `:136,209` for the empty-state siblings)
**Issue:** `#rfd-stats`, `#rfd-active`, `#rfd-ores` and `#rfd-history` are empty in the built HTML and
filled by the client script. When there is nothing to render, the script leaves them empty and shows
the sibling `#rfd-active-empty` / `#rfd-history-empty` cards instead — but those siblings carry no
`data-help`. An empty block element has zero height, so `html[data-help-on] [data-help]{outline:…}`
draws a hairline that is neither visible nor hoverable.

**Failure scenario:** brand-new account, no orders logged → `/refinery.html` → help on. Four of the
eight explanations (`.ctl.stats`, `.ctl.active`, `.ctl.ores`, `.ctl.history`) have no visible outline
and no reachable hover target, while the three visible "nothing here yet" cards next to them explain
nothing. The visitor who most needs the tracker explained — the one who has never used it — gets half
the help.

**Fix:** move the anchor up to the section wrapper that contains both the list and its empty-state card,
or duplicate the same `data-help` value onto `#rfd-active-empty` / `#rfd-history-empty`. For `#rfd-ores`,
put it on the enclosing `.acx-field` (`:165`) so the "+ Erz" button is covered too.

### IN-01: `data-tool-id` on the toggle button is dead

**File:** `src/components/ToolHelp.astro:51`
**Issue:** `tool-help.js` only reads `data-tool-id` from `details.tool-help` (`:55-56`); the copy on the
`<button>` is never read by any code. It also doubles every page's `data-tool-id` count, which is
harmless only by accident (assertion 3 compares EN against DE, assertion 4 de-duplicates in a `Set`).

### IN-02: The eleven tool ids exist as untyped string literals in three unconnected places

**File:** `src/components/ToolHelp.astro:28` (`tool: string`), the eleven call sites, `scripts/verify-help.mjs:56`
**Issue:** `Props.tool` is `string`, so `<ToolHelp tool="itemfindr" …/>` type-checks; it only fails at
build time via the `useHelp` throw. The verify script keeps its own hand-maintained `TOOL_IDS` copy,
which can drift from the catalog in the "id removed" direction without any check noticing.
**Fix:** export `type ToolId = 'itemfinder' | … ` from `help.ts`, type `Props.tool` with it, and derive
`TOOL_IDS` from the catalog keys (or at minimum assert in `assertHelpParity()` that every id in a
declared list has a `.title`/`.purpose`).

### IN-03: `steps: 3 | 4 | 5` is dead flexibility

**File:** `src/components/ToolHelp.astro:30,36`
**Issue:** The catalog only ever defines `step1..step4` for all eleven tools and all eleven call sites
pass `steps={4}`. `steps={5}` type-checks and then throws in `useHelp` during `astro build`; `steps={3}`
silently drops a documented step.
**Fix:** narrow to `steps?: 4` (or add the `step5` keys if a five-step tool is actually planned).

### IN-04: The gate that certified the phase is not reachable through its own npm script

**File:** `package.json:13`
**Issue:** `"verify:help": "node scripts/verify-help.mjs"` runs *without* `--complete`, so the coverage
assertion only reports its state and never fails. The "11 von 11" claim requires
`npm run verify:help -- --complete`, which nothing runs automatically (deliberately not wired into
`npm run build`, per the script header). A tool losing its ToolHelp entirely would not be caught by any
routine run.
**Fix:** add a second entry `"verify:help:complete": "node scripts/verify-help.mjs --complete"` and call
it from the same place `verify:fx` is called.

### IN-05: `stripComments()` also strips comment-like text inside string literals

**File:** `scripts/verify-help.mjs:71-73`
**Issue:** `code.replace(/\/\/.*$/gm, '')` truncates any line containing `//` inside a string (a URL,
a regex), and `/\/\*[\s\S]*?\*\//g` eats from a `/*` inside a string to the next `*/`. Harmless today
because the outside region of `tool-help.js` contains no such literal, but assertion 1 is a pure text
search over the result — a future string could hide a banned identifier from it.
**Fix:** note the limitation next to the existing A3 caveat in the header, or tokenize properly.

### IN-06: Five "steps" are statements of fact rendered as numbered instructions

**File:** `src/i18n/help.ts:135,136,137` (`armorsets.step2/3/4`), `:146,148` (`wikelo.step2/step4`); rendered by `src/components/ToolHelp.astro:43-47`
**Issue:** "Jedes Set zeigt seine Teile nach Körperzone gegliedert." and "Weiter unten stehen die drei
Stationen und der Patch-Verlauf." are descriptions, not operating steps, but `ToolHelp` renders them
inside `<ol class="tool-help__steps">` as items 2-4 of a numbered instruction list. DOC-01 asks for
"zuerst den Zweck, dann die Bedienung"; on these two pages steps 2-4 are more purpose.
**Fix:** fold the descriptive lines into `.purpose` and keep the `<ol>` for the genuinely actionable
ones, or let `ToolHelp` accept `steps={2}` for pages with only two real steps (see IN-03).

## Fix Outcome (2026-08-06)

Scope per fixer instructions: CR-01, CR-02, CR-03, WR-05 only. WR-01, WR-03,
WR-04, WR-06, WR-07 and all Info items were deliberately left (WR-01 and WR-03
explicitly out of scope; WR-04/WR-06/WR-07/IN-* not requested).

### CR-02: fixed (commit `baf9df8`)
`#tool-help__bubble` now has `pointer-events:none`, and `mouseout`/`focusout`
listeners (`onLeave`) hide the popover and clear its description whenever the
pointer or focus leaves the current `[data-help]` anchor for a different one.
Matching `removeEventListener` pair added to `deactivate()`.

### CR-01: fixed (commit `baf9df8`)
New `place(el)` clamps the anchor's visible top/bottom against the viewport,
flips the bubble above the anchor when there is no room below, and clamps
left/right against `bubbleEl.offsetWidth`. Adapted from the review's snippet:
measurement now happens **after** `showPopover()` (not before) because the
popover is `display:none` while closed and `offsetWidth`/`offsetHeight` would
read 0 beforehand — the review's own snippet order would not have worked.

### CR-03: fixed (commit `baf9df8`)
`onPoint` now writes `aria-describedby` onto `e.target` when the event is
`focusin` (the actually focused control), falling back to the `[data-help]`
wrapper for `mouseover`. A single `describedEl` tracking variable (rather than
the review's `closest()` re-lookup in `onLeave`, which would have missed
descendant targets) is cleared and the attribute removed in both `onLeave` and
`deactivate()`, so it never survives past the bubble it points at. This also
