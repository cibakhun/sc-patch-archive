## Summary

This phase adds no new libraries, no build step, and no runtime dependency — it is pure vanilla HTML/CSS/JS layered onto ten existing, already-idiosyncratic tool bodies. The two structural questions that matter for planning are (1) where the entry point physically goes in nine different, non-uniform toolbar markups, and (2) how a JS-driven "highlight + explain" layer can attach reliably to widgets where **two of the ten tools rebuild their filter-chip DOM from scratch on every interaction** (Item Finder, and to a lesser degree Mining) while the other eight render their controls once, server-side, and never touch that DOM again.

The direct precedent, `FxToggle.astro`, is a *good* model for a **static, always-present** tooltip (Stage 1's purpose text needs nothing more than a native `<details>`/`<summary>` — even simpler than FxToggle, and truly free per D-11). It is **not** a workable model for Stage 2's per-element bubbles, because a pure-CSS `:hover`/`:focus-visible` tooltip has no Esc handling — Esc doesn't move focus, so CSS alone cannot close it (DOC-05 requires Esc-to-close). D-11 already anticipates that Stage 2 needs JS ("Horcher" = listener). The clean solution is the native `popover` attribute (Baseline Widely Available since April 2025, Chrome 114+/Firefox 132+/Safari 17+ — comfortably supported by 2026), which gives Esc-dismiss, light-dismiss (click outside), and single-open-at-a-time semantics (`popover="auto"`) for free, matching D-01's "one bubble at a time" requirement without hand-rolling any of that.

The single riskiest technical trap in this phase is **`useTranslations()`'s silent EN-fallback** (`UI[lang]?.[key] ?? UI[DEFAULT_LOCALE][key] ?? String(key)`, `src/i18n/ui.ts:794`). This is the exact opposite of DOC-04 ("keine Fassung fällt auf die andere Sprache zurück"). If help text is authored in `ui.ts` and consumed via the existing `t()` helper, a missing DE key will silently render in English and nothing will fail — violating DOC-04 invisibly. The research recommends a **separate, stricter accessor** for help content (see Pitfall 1) plus a build-output assertion mirroring `scripts/verify-fx.mjs`'s pattern.

**Primary recommendation:** Build one shared, site-wide-loaded script (`assets/tool-help.js`, modeled on the existing `assets/offcanvas.js` pattern — loaded via `<script defer>` in `Layout.astro`, inert unless the page contains the relevant markup) that implements the generic "outline + popover" engine keyed off a `data-help="<key>"` attribute convention. Each of the ten tool components/pages gets: (a) a `<details>` purpose block inserted at its own located toolbar anchor (table below), containing (b) an "Elemente erklären" toggle button, and (c) `data-help` attributes added to the STABLE wrapper elements of each control type (never to elements that get destroyed/recreated by `innerHTML =` replacement — see Pitfall 2). Content lives in a new `src/i18n/help.ts` module (Discretion — justified below) with a same-shape `{ de: {...}, en: {...} }` object and its own non-fallback-on-missing accessor.

### Pattern 1: Stage-1 purpose disclosure — pure `<details>`, D-09's open-on-first-visit resolved client-side

**What:** Server renders `<details class="tool-help">` closed by default (safe SSR default — no flash of open content for repeat visitors, matches D-12's "don't crowd out the meta description" concern since it's closed text either way for SEO purposes — the text is in the DOM regardless of `open` state and is crawlable either way).

**Why client-side, not server-side, for the open/closed decision:** Astro's SSR has no access to the visitor's `localStorage` at build/request time (this is a fully static build — there is no per-request server logic at all, per `Out of Scope: "Serverseitige Renderlogik"`). The only place D-09's "open on first visit" can be decided is client-side, after hydration reads `localStorage`.

**When to use:** Every one of the ten tool pages, once, at its located toolbar anchor.

**Example:**
```html
<!-- SSR: closed by default -->
<details class="tool-help" data-tool-id="itemfinder">
  <summary>{t('help.itemfinder.button')}</summary>
  <p>{t('help.itemfinder.purpose')}</p>
  <ol>
    <li>{t('help.itemfinder.step1')}</li>
    <li>{t('help.itemfinder.step2')}</li>
  </ol>
  <button type="button" class="tool-help__elbtn" data-tool-id="itemfinder">
    {t('help.elementsButton')}
  </button>
</details>

<script>
// Tiny inline snippet, same technique as Layout.astro's data-theme/data-fx
// head flags — runs before first paint is NOT required here (unlike theme,
// there's no flash-of-wrong-content risk for a closed <details>), so this
// can run on DOMContentLoaded rather than needing head-of-document placement.
(function () {
  var KEY = 'vb.help.seen'; // ONE localStorage entry for all ten tools (D-09)
  var seen = {};
  try { seen = JSON.parse(localStorage.getItem(KEY) || '{}'); } catch (e) {}
  document.querySelectorAll('details.tool-help').forEach(function (d) {
    var id = d.getAttribute('data-tool-id');
    if (!seen[id]) {
      d.open = true;
      seen[id] = 1;
    }
  });
  try { localStorage.setItem(KEY, JSON.stringify(seen)); } catch (e) {}
})();
</script>
```

### Pattern 2: Stage-2 element-help engine — activation-time DOM query + native `popover`

**What:** A single shared script, loaded once site-wide (like `offcanvas.js`), that does nothing until a `.tool-help__elbtn` is clicked.

**When to use:** All ten tools share this ONE script; only the `data-help="<key>"` attributes differ per tool.

**Example:**
```js
// assets/tool-help.js — loaded via <script defer> in Layout.astro, like offcanvas.js.
// Registers exactly ONE click listener at load (cheap, matches offcanvas.js's
// own baseline cost) and does NOTHING else until a help button is pressed —
// no mouseover/focusin listener, no loop, no fetch before that (D-11/DOC-06).
(function () {
  'use strict';
  var active = null; // currently-active tool id, or null

  function activate(toolId) {
    // Query the LIVE DOM now, not a reference captured earlier — this is
    // what makes Item Finder's rebuilt chip wrappers safe to target: the
    // wrapper node (#uif-kind-chips etc.) persists across innerHTML resets,
    // so querying at activation time always finds the current instance.
    var targets = document.querySelectorAll('[data-help]');
    targets.forEach(function (el) {
      var box = document.createElement('div');
      box.className = 'tool-help__outline';
      // position via getBoundingClientRect(), appended to a single overlay
      // layer — omitted here for brevity, same technique as offcanvas.js's
      // scrim element.
      el.__helpOutline = box;
      document.body.appendChild(box);
    });

    // ONE delegated listener, added only now — removed on deactivate.
    document.addEventListener('focusin', onFocus);
    document.addEventListener('mouseover', onHover);
    document.addEventListener('keydown', onKeydown);
    active = toolId;
  }

  function deactivate() {
    document.querySelectorAll('.tool-help__outline').forEach(function (b) { b.remove(); });
    document.removeEventListener('focusin', onFocus);
    document.removeEventListener('mouseover', onHover);
    document.removeEventListener('keydown', onKeydown);
    var bubble = document.getElementById('tool-help__bubble');
    if (bubble && bubble.hasAttribute('popover')) bubble.hidePopover();
    active = null;
  }

  function showBubbleFor(el) {
    var bubble = document.getElementById('tool-help__bubble');
    var key = el.getAttribute('data-help');
    bubble.querySelector('.tool-help__bubble-text').textContent =
      (window.__TOOL_HELP_TEXT && window.__TOOL_HELP_TEXT[key]) || '';
    // Native popover: Esc-to-close and light-dismiss are FREE here.
    bubble.showPopover();
    // position bubble near el via getBoundingClientRect() — omitted.
  }

  function onFocus(e) {
    var el = e.target.closest('[data-help]');
    if (el) showBubbleFor(el);
  }
  function onHover(e) {
    var el = e.target.closest('[data-help]');
    if (el) showBubbleFor(el);
  }
  function onKeydown(e) {
    if (e.key === 'Escape' && active) deactivate(); // also fully exits help mode
  }

  document.addEventListener('click', function (e) {
    var btn = e.target.closest('.tool-help__elbtn');
    if (!btn) return;
    var toolId = btn.getAttribute('data-tool-id');
    if (active === toolId) deactivate();
    else activate(toolId);
  });
})();
```

```html
<!-- ONE bubble element, reused for every anchor, present once per page. -->
<div id="tool-help__bubble" popover="auto" role="tooltip">
  <span class="tool-help__bubble-text"></span>
</div>
```

### Anti-Patterns to Avoid
- **Caching `document.querySelectorAll('[data-help]')` once at page load or at `activate()`-call-time-only-then-reusing-across-re-renders:** Item Finder replaces the innerHTML of its chip wrappers on every click; a stale NodeList from before that replacement points at detached nodes. Re-query fresh on every `activate()` call at minimum; if help mode can remain ON while the user keeps filtering, also re-query (or use a `MutationObserver`) on every re-render.
- **Attaching `data-help` to individual chip `<button>` elements inside `#uif-kind-chips` etc.:** those buttons are destroyed and recreated by `wrap.innerHTML = kinds.map(...).join('')` (`assets/item-finder-app.js:285`); any attribute placed on them by JS after the fact is wiped on the next click. Tag the wrapper (`#uif-kind-chips`), not its children — this also matches D-03's "once per KIND, not per occurrence."
- **Using `useTranslations()`/`t()` from `src/i18n/ui.ts` for help copy without a stricter wrapper:** see Pitfall 1.
- **Registering the `mouseover`/`focusin` listeners unconditionally at page load "for convenience":** directly violates D-11/DOC-06 ("kein Horcher... vor dem Druck auf 'Elemente erklären'"). Attach only inside `activate()`, remove inside `deactivate()`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| Esc-to-close + outside-click-to-close for the element-explanation bubble | A custom `keydown` global listener tracking a "help mode" boolean + manual outside-click detection with `event.target.closest()` guards | Native `popover="auto"` attribute | Browser-native light-dismiss and Esc handling, focus-return semantics, and "closes other auto-popovers when a new one opens" all come for free; this is exactly D-01's "one bubble at a time" behavior without writing it |
| Keyboard-openable/closable Stage-1 disclosure | Custom `aria-expanded` button + manually toggled `hidden` attribute + `keydown` Enter/Space handler | Native `<details>`/`<summary>` | Zero JS, correct semantics out of the box, and it is literally what the element is for |
| DE/EN structural parity checking for the new help content | A manual checklist or "remember to update both files" comment | A build-output assertion script modeled on `scripts/verify-fx.mjs` (counts occurrences of help markers in `dist/index.html` vs `dist/de.html`-equivalent pairs) | The codebase already has this exact class of bug (`.planning/codebase/CONCERNS.md` Class A) and an established, working countermeasure pattern — reuse it rather than trusting hand-discipline |

**Key insight:** every mechanism this phase needs (disclosure widget, dismissible bubble, cross-instance persistence) already has a native HTML/browser primitive as of 2026. The temptation in a bundler-free, no-framework codebase is to write more JS than needed "because there's no framework helping"; the opposite is true here — native elements need *less* JS than a hand-rolled version would.

## Common Pitfalls

### Pitfall 1: `useTranslations()`'s silent EN-fallback is the opposite of DOC-04
**What goes wrong:** `src/i18n/ui.ts:794` — `UI[lang]?.[key] ?? UI[DEFAULT_LOCALE][key] ?? String(key)`. If a DE help key is missing, `t()` silently returns the English string. Nothing crashes, nothing warns, no visual difference on the DE page other than the text being in the wrong language.
**Why it happens:** This fallback exists on purpose for the general nav/chrome catalog (`src/i18n/ui.ts:11`: "Fehlt ein Key in einer Sprache, fällt t() sichtbar auf EN zurück statt zu crashen" — note "sichtbar" there means "visibly [in English]," not "with a visible warning"). DOC-04 explicitly forbids exactly this behavior for help text.
**How to avoid:** Do not reuse `t()`/`useTranslations()` for help copy. Either (a) write a second accessor in the new help module that throws/logs at build time if a key is missing in either locale (checkable at Astro build time since both objects are static literals — a simple `Object.keys(de).length !== Object.keys(en).length` check, or per-key diff, run once at module load or via a small Node check script), or (b) add an explicit assertion to the phase's verification script (see Pitfall 3) that greps built DE/EN pages for equal counts of help-related markers, mirroring `verify-fx.mjs` assertion 6.
**Warning signs:** A DE tool page showing English sentences inside the purpose/step text with everything else (labels, buttons) correctly in German — easy to miss in a quick visual pass because it reads fine, just in the wrong language.

### Pitfall 2: Two different render lifecycles hiding under "clientseitig gerendert"
**What goes wrong:** CONTEXT.md's canonical refs list Item Finder AND Crafting together as "clientseitig gerendert," which could lead a planner to write one blanket "must use event delegation everywhere" task. Direct inspection shows Crafting's filter sidebar (checkboxes, category list) is 100% SSR'd at build time from `catList.map()` — it is never touched by `innerHTML =`. Only Item Finder's chip groups are actually rebuilt from scratch on interaction.
**Why it happens:** "Client-rendered" is true of both apps' *data* (both fetch a `*-db.json` and render result cards/details in JS), but is not true of both apps' *filter controls*.
**How to avoid:** Use the per-tool table above. Write `data-help` directly into `.astro` templates for 9 of 10 tools (safe, simple). Only for Item Finder, verify the `data-help` attribute is placed on the persistent wrapper `<div id="uif-kind-chips">` (etc.) rather than relying on it surviving inside the `.innerHTML =` payload.
**Warning signs:** A `data-help` attribute mysteriously disappearing after the first click on any Item Finder filter chip — that is the `innerHTML =` replacement wiping it.

### Pitfall 3: "Costs nothing until opened" needs a build-output assertion, not a promise
**What goes wrong:** DOC-06 and D-11 are easy to satisfy accidentally at first (e.g., during development) and easy to regress later (a future change adds a "helpful" `mouseover` listener at module scope "just for logging," reintroducing constant work). Nyquist validation is disabled for this project (`workflow.nyquist_validation: false` in `.planning/config.json`), so there is no automatic per-requirement test map — the phase must supply its own gate, same as Phase 01.1 did with `verify-fx.mjs`.
**Why it happens:** JS event listeners and small parse costs are invisible in casual manual testing; only profiling or code inspection catches "the script now does something before activation."
**How to avoid:** Write a `scripts/verify-help.mjs` (or extend `verify-fx.mjs`'s sibling pattern) that greps the BUILT `dist/assets/tool-help.js` for statically-verifiable structural markers — e.g., assert that `addEventListener('mouseover'` / `addEventListener('focusin'` / `requestAnimationFrame(` / `setInterval(` do NOT appear inside the top-level IIFE body outside the `activate()` function (a regex-based heuristic is enough, matching the spirit of `verify-fx.mjs`'s assertions 1-3). Also assert DE/EN parity of the count of `class="tool-help"` / `data-help=` occurrences per page-pair, mirroring assertion 6 of `verify-fx.mjs`.
**Warning signs:** Chrome DevTools Performance tab showing any scripting activity attributable to `tool-help.js` before the "Elemente erklären" button is ever clicked.

### Pitfall 4: `versioned()`'s memoized sha1 needs a dev-server restart after editing `tool-help.js`
**What goes wrong:** `src/lib/assetVersion.ts` memoizes the sha1 hash per Node process (`memo.get(file)`); the Astro dev server does not re-read the file after the first request. Editing `assets/tool-help.js` during development and refreshing the browser can silently serve the OLD hash's cached response from Cloudflare/browser cache, or — more commonly in local dev — simply not reflect changes because the dev server itself never recomputes.
**Why it happens:** Documented project-wide gotcha (see MEMORY.md "Bildlaufleisten site-weit versteckt": "Dev-Falle: `versioned()` memoisiert den sha1 → Dev-Server nach Asset-Änderung neu starten").
**How to avoid:** Restart `npm.cmd run dev` after any edit to `assets/tool-help.js` (or any new CSS file this phase adds) during manual testing.
**Warning signs:** A JS/CSS change that "does nothing" in the browser despite a hard refresh.

### Pitfall 5: `assets/theme.css` is generated — new help styling needs its own file
**What goes wrong:** Any hand-edit to `assets/theme.css` is silently discarded by the next `npm run theme` run.
**Why it happens:** Documented project convention; `theme.css` is produced by `scripts/build-light-palettes.mjs` + `scripts/tokenize-theme-colors.mjs` + `scripts/build-light-overrides.mjs`.
**How to avoid:** Put the outline/bubble/details styling in its own new file (e.g. `assets/tool-help.css`, loaded via `versioned()` in `Layout.astro` like `mobile-ux.css`) or inline `<style>` inside the shared component, never in `theme.css`. Reference existing CSS custom properties (`--surface`, `--accent`, `--line`, `--muted`) rather than hardcoding colors, matching `FxToggle.astro`'s own approach (it never touches `theme.css` either — it defines local rules that reference the shared tokens).
**Warning signs:** New help styling that looks correct after editing, then reverts after the next unrelated `npm run theme` invocation.
