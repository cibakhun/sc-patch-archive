## Summary

This phase is pure codebase surgery, not library selection: there is no framework or package
to evaluate, only three duplicated `requestAnimationFrame` loops and one duplicated pointer-glow
element to gate or remove across a hand-maintained bilingual tree. The two hard technical
problems are (1) making a self-rescheduling `tick()` loop start only on request and stop
mid-session without a reload, and (2) proving both the removal (`.cursorglow`, 107 files) and
the gate (`#stars`/`#embers`, 3 loop implementations) are complete and DE/EN-symmetric, given
that nothing in this repo's build compares language pairs (CONCERNS.md Class A).

The repo already contains the exact pattern needed for both problems, in two different places:
`assets/archive.js`'s starfield (`assets/archive.js:321-420`) already implements a clean
start/stop/restart cycle via a `running` boolean gate at the reschedule call site, and
`src/layouts/Layout.astro:119-129` + `:278-304` already implements a synchronous pre-paint
head flag + delegated-click + `storage`-event toggle for `vb.theme`. Building the FX gate is
mechanically "do what `archive.js` already does for visibility, wired to what `Layout.astro`
already does for `vb.theme`, minus the admin gate, defaulted to off." The removal of
`.cursorglow` is a pure byte-identical string deletion across 107 files, for which
`scripts/tokenize-theme-colors.mjs` is the correct in-repo template (dry-run, exact-match
assertion, report-don't-guess on anything unexpected).

**Primary recommendation:** Build one small shared gate in `Layout.astro` (localStorage key
`vb.fx`, `data-fx="on"|"off"` on `<html>`, set synchronously in `<head>` before first paint,
default `off`, `prefers-reduced-motion` always wins), broadcast changes via a custom DOM event
so all three loop consumers can react live, and let each loop read `document.documentElement.
getAttribute('data-fx')` at both its start point and its `requestAnimationFrame` reschedule
call site (copying `archive.js`'s existing `running`-flag idiom). Remove `.cursorglow` (element,
CSS rule, listener) via a Node codemod under `scripts/`, verified by an exact pre/post
occurrence count and a post-build grep of `dist/**/*.html` (the same "verify against dist"
convention `scripts/_verify.mjs` already uses).

### Pattern 1: Gate at the reschedule call site (recommended technique for Q1/Q2)

**What:** Each loop already has exactly one line that calls `requestAnimationFrame(tick)` to
continue itself. Wrap that one line in the flag check, and track a `running` boolean so a
restart doesn't double-start.

**When to use:** Any self-rescheduling `tick()`-style loop that must be startable/stoppable
without a reload.

**Why this is the minimal-diff, most robust option (compared against the alternatives from
CONTEXT.md's `research_questions`):**
- *Gating only the start call site* (not the reschedule): fails FX-05 outright per D-09 — a
  loop already running when the user toggles off would never see the start-site check again.
- *A shared `raf` wrapper function*: would require touching every `requestAnimationFrame(...)`
  call across 3 differently-styled files (ES5 IIFE, ES6 arrow-function inline scripts, and a
  `'use strict'` module) to route through one helper, and that helper would need to be loadable
  from all three contexts, which patch pages (no external script tag beyond their own inline
  block) don't have. More moving parts for the same outcome.
- *`cancelAnimationFrame` with a stored handle*: correct for "stop", but does nothing for
  "don't double-start on re-enable" (see Q2) — you'd still need the `running` boolean on top,
  making it strictly more code for no extra safety. It also requires a new module-scope variable
  (`rafId`) in every one of the 38 loop copies, whereas the boolean-gate approach reuses a
  variable (`running`) that **already exists** in `archive.js`.
- *An abort flag checked inside the draw loop body (not at reschedule)*: functionally identical
  to gating the reschedule call site if written correctly, but is easy to get subtly wrong (e.g.,
  checking the flag before `draw()` still leaves the reschedule line unconditional, so the loop
  keeps ticking forever just skipping the paint — CPU cost only drops for the canvas paint, not
  the JS wake-up-every-16ms cost, which is exactly what FX-02 is trying to eliminate). Gating the
  reschedule *call itself* is the only technique that actually removes the frame from the
  browser's animation-frame queue.

**Recommendation: gate the reschedule call site, using a `running` boolean per loop instance —
this is Pattern 1, and it is already implemented correctly in this repo today** for a different
purpose (tab visibility) at `assets/archive.js:398-419`:

```js
// Source: assets/archive.js:333, 398-419 (existing, unmodified — visibilitychange gate)
var running = true;
function frame() {
  if (!running) return;
  draw();
  requestAnimationFrame(frame);
}
// ...
document.addEventListener('visibilitychange', function () {
  if (document.hidden) {
    running = false;
  } else if (!running) {
    running = true;
    requestAnimationFrame(frame);
  }
});
frame();
```

The FX gate is the *same shape*, with the condition swapped from `document.hidden` to the FX
flag, and the trigger swapped from `visibilitychange` to the new `vbfxchange` custom event
(plus reading the flag once at the initial `frame()`/`tick()` call so a cold load with FX off
never starts at all — satisfying FX-02):

```js
// Recommended pattern (new code, not yet in the repo — apply to all 3 loop sites)
function fxOn() { return document.documentElement.getAttribute('data-fx') === 'on'; }
var running = false;
function tick() {
  if (!running) return;
  draw();               // existing draw body, unchanged
  requestAnimationFrame(tick);
}
document.addEventListener('vbfxchange', function (e) {
  if (e.detail.on && !running) { running = true; requestAnimationFrame(tick); }
  else if (!e.detail.on) { running = false; }           // next frame simply won't reschedule
});
if (fxOn()) { running = true; requestAnimationFrame(tick); }  // cold-load start, gated
```

Reading the `data-fx` DOM attribute (rather than a JS variable exported from another script) is
the right choice for D-11's ordering constraint: the attribute is written synchronously in
`<head>` before ANY body script parses, so it is guaranteed present and correct by the time
`detail.js`, the patch-page inline script, or `archive.js` execute — regardless of script load
order between files, which a JS-variable handoff could not guarantee as cleanly.

### Pattern 2: Runtime-created canvas (`#embers`) needs its creation ungated from its animation

**What:** `#embers` does not exist in any page's static markup — it is created by
`document.createElement('canvas')` inside `detail.js` (`assets/detail.js:104-112`), currently
gated only by `!reduce && accentIsWarm()`.

**Answer to Q2 ("does re-enabling need to re-create it?"):** No, if the element creation and the
animation start are separated. Recommendation: **always create the `#embers` element** (cheap —
one DOM node) on pages where `accentIsWarm()` is true and `!reduce`, exactly as today, but do
**not** call `esize()`/start `etick()` at creation time unless `fxOn()`. On a later toggle-ON,
call `esize()` again (window may have been resized while the canvas was dormant — the existing
`resize` listener stays attached and harmless even while not running, since `esize()` only
rebuilds the particle array, it doesn't paint) then start `etick()` guarded by the same
`running` boolean as Pattern 1. This avoids ever needing to re-create the canvas element,
avoids a second `document.body.appendChild` call, and keeps `#embers`' DOM lifetime identical to
today (created once per page load) — satisfying D-07 ("Leinwände bleiben im Bestand").

### Pattern 3: CSS hides the frozen frame; JS stops the scheduling — the two are not redundant

**What:** D-10 requires a CSS rule alongside the JS gate. This is not belt-and-suspenders
redundancy — the two solve different moments:
- **JS gate (Pattern 1)** prevents new frames from being *scheduled* — it has no effect on
  pixels already painted onto the canvas by the last frame that ran before toggle-off.
  `<canvas>` retains its last painted bitmap until something clears or hides it.
  `[VERIFIED: MDN Canvas API — canvas content persists until cleared, training knowledge cross-checked against no session source, tagged ASSUMED below]`
- **CSS rule** is what actually removes that stale bitmap from the screen, and it takes effect
  on the very next style recalc/paint — faster and more certain than waiting for the JS gate's
  next would-be animation frame.

```css
/* Recommended — add near the existing .cursorglow / #stars / #embers rules in detail.css
   and duplicate into the patch-page inline <style> blocks alongside the codemod's removal work */
html:not([data-fx="on"]) #stars,
html:not([data-fx="on"]) #embers {
  display: none;
}
```

Note this rule must NOT be scoped only to `assets/detail.css` — the 38 patch pages define
`#stars{...}` inline per-page (CONCERNS.md "Copy-pasted page chrome" section) and `archive.css`
defines `.space__stars` separately again. All three CSS surfaces need the equivalent rule, or a
shared selector reachable from all three (the `[data-fx]` attribute selector on `<html>` is
reachable from every stylesheet on every page since it's set on the document root, so the *same*
rule text can be pasted into `detail.css`, each patch page's inline `<style>`, and `archive.css`
without any cross-file dependency — this is consistent with the "seitenlokal dupliziert"
established pattern this phase is explicitly not asked to undo).

### Anti-Patterns to Avoid
- **Gating with `display:none` alone (CSS-only fix):** Explicitly ruled out by D-08 — stops
  nothing, the rAF loop keeps firing every ~16ms against an invisible canvas, which is the exact
  power-consumption complaint from the feedback. This is the single most important pitfall in
  this phase — it is easy to "fix" the visible symptom and miss the CPU cost entirely, and FX-02
  is specifically written to be checked by measurement, not code reading, to prevent exactly
  this outcome.
- **Storing the FX flag only as a JS variable, not a DOM attribute:** Breaks D-11's ordering
  guarantee — script execution order across `detail.js`, inline patch scripts, and `archive.js`
  relative to each other and to any future script is not something this codebase enforces or
  should have to enforce. The DOM attribute is available synchronously to every consumer
  regardless of script order.
- **Removing `.cursorglow`'s CSS rule but leaving `--mx`/`--my` writes, or vice versa:** D-02 is
  explicit that all three pieces (element, rule, listener) must go together — the listener alone
  ("teuerste Teil") is the actual performance win; leaving it in place while deleting only the
  visible div/rule would look fixed but leave the root-element style recalculation on every
  `pointermove` untouched.

## Common Pitfalls

### Pitfall 1: Fixing the symptom (visible glow) but not the cost (style recalc on every pointermove)
**What goes wrong:** A change that hides `.cursorglow` visually (e.g., `opacity:0` or
`display:none` via CSS only) ships, looks correct in a screenshot, and the `pointermove`
listener writing `--mx`/`--my` onto `<html>` keeps running on every mouse move regardless.
**Why it happens:** The visible complaint (the glow) and the actual performance cost (root-
element custom-property writes on every `pointermove`, at native mouse-poll rate) are two
different things, and only one of them is visible without profiling.
**How to avoid:** D-02's explicit three-part checklist (element + rule + listener) exists
precisely for this reason. Verification must grep for `--mx`/`--my` writes and `pointermove`
listeners referencing them, not just for the `<div class="cursorglow">` markup.
**Warning signs:** A grep for `class="cursorglow"` returns zero matches, but a grep for `--mx`
still returns hits in `assets/detail.js` or patch pages.

### Pitfall 2: Treating the star canvases as always drawing at full cost, missing the outlier
**What goes wrong:** A codemod or manual edit assumes every file with `id="stars"` runs the same
star-twinkle loop and gates them identically — but `src/pages/patches/sc-4-2-0.astro` (+ DE
twin) reuses the same canvas ID for rain/lightning (`drops`, `boltPts`, `performance.now()`),
a structurally different loop with its own reschedule call site.
**Why it happens:** Grepping for `id="stars"` or `#stars` finds the canvas element, not the loop
body — the loop body's shape differs on this one outlier pair.
**How to avoid:** Any codemod targeting the loop *body* (not just the element) must special-case
or explicitly skip `sc-4-2-0.astro`/its DE twin and gate that file's rain/lightning loop
separately by hand, verifying its own reschedule call site.
**Warning signs:** A codemod's "expected N matches" assertion for the loop-tail pattern comes up
2 short, or 2 over, of the patch-page total — that delta is this outlier pair.

### Pitfall 3: `archive.js`'s starfield is the longest-lived loop on the site, not the smallest
**What goes wrong:** Prioritizing `detail.js` (69+ pages) and the 36 patch-page loops as "the
big win" while treating `archive.js`'s starfield as a minor third case, because it's only one
file.
**Why it happens:** File count (1) undersells impact. `.space` (the starfield's container) is
`position:fixed; inset:0; z-index:-1` covering the *entire* `/archiv` page
(`assets/archive.css:163-178`), which per ROADMAP.md is one of the two pages the feedback cites
scanning behavior on ("Werkzeugseiten ... sind der Prüfort"), and per the feedback quote itself,
`/archiv` browsing is exactly the kind of long-lived, list-scanning session where idle CPU use
matters most.
**How to avoid:** Treat all three loop sites as equally in-scope, verify each independently
rather than assuming a fix in `detail.js` covers "most of the site."
**Warning signs:** A verification pass that samples only tool pages (item-finder, crafting,
mining) and never loads `/archiv` or `/archiv/de` to confirm its starfield also honors the gate.

### Pitfall 4: The `?nofx` escape hatch creates a false sense that FX-02 is already solved
**What goes wrong:** `?nofx` exists today on exactly 10 files (`item-finder.astro`,
`feedback.astro`, `downloads.astro`, `topics/mining.astro`, `topics/crafting.astro` × DE/EN) and
*does* remove the `#stars` element before `detail.js`'s loop checks for it — so on those 10
files with `?nofx` appended, the loop genuinely never starts. It is easy to test one of these
URLs, see zero rAF calls, and wrongly conclude the site-wide default-off requirement (FX-02) is
already met.
**Why it happens:** `?nofx`'s coverage (10 of 107+ files) and mechanism (query-string, not
persisted, not respected by `archive.js` or the 36 patch-page loops, does not touch `#embers`)
looks superficially similar to what FX-02/FX-03 ask for, but solves a much smaller, non-
persistent, single-page-type subset.
**How to avoid:** Verification for FX-02 must test URLs **without** `?nofx` on pages that never
had it (patch pages, `/archiv`) as the primary evidence, not rely on the existing escape hatch.
**Warning signs:** A verification note that only ever tested `*?nofx` URLs.

**RESOLVED 2026-07-29 (Frage 1):** Der Umschalter bleibt immer sichtbar und bedienbar;

**RESOLVED 2026-07-29 (Frage 2):** Die Browser-Werkzeuge dieser Umgebung können
JavaScript in einer GELADENEN Seite auswerten. Eine Injektion vor der Navigation ist
dafür nicht nötig: Wird `window.requestAnimationFrame` NACH dem Laden umschlossen,
zeigt eine laufende Schleife ~60 Aufrufe/s (sie meldet sich jedes Bild neu an), eine
vollständig gegatterte Seite null. Der Plan trägt zusätzlich eine Gegenprobe
(FX an muss ≥100 Aufrufe/3 s zeigen) — ohne sie wäre „0 Aufrufe" auch durch eine
kaputte Messung erfüllt.

1. **Should the toggle UI be hidden entirely when `prefers-reduced-motion: reduce` is active, or remain visible-but-overridden?**
   - What we know: D-12 requires the effective FX state to stay off when reduce is active,
     regardless of the stored preference. FX-04 requires the toggle be reachable by "ALLE
     Besucher" (all visitors) — reduce is one specific visitor state, not a role.
   - What's unclear: whether "reachable for all" implies the toggle must remain visibly
     interactive even for reduce users (recording their intent for a future non-reduce session
     or device), or whether showing a control that visibly does nothing is itself a worse UX.
   - Recommendation: keep the toggle visible and interactive always (mirrors `ThemeToggle.astro`
     which has no reduce-motion special case at all), and let the stored preference persist even
     while overridden — this is the smaller, more consistent change and avoids adding a third
     visibility condition (admin / reduce / — ) to a component whose whole point in this phase is
     to be simpler than `ThemeToggle`, not more conditional. Flag this interpretation to the user
     during planning rather than deciding it silently, since D-12's wording ("schlägt die
     gespeicherte Wahl") is about the *effective* state, not the control's visibility.

2. **Exact real-browser technique for the FX-02 "Bildrate im Leerlauf ist null" measurement.**
   - What we know: the most direct, false-positive-resistant technique is to override
     `window.requestAnimationFrame` with a counting wrapper *before* any page script runs (a
     pre-navigation/init script), then sample a window of idle time (recommend ≥3s, starting
     ≥2s after load so any one-shot entrance animations — e.g. `.count[data-to]` counters, which
     use rAF for ~1.1s and would otherwise be a false positive — have already finished) and
     assert the counter is 0.
   - What's unclear: whether the `agent-browser` skill available in this session's toolset
     exposes an equivalent of Playwright's `addInitScript`/CDP `Page.addScriptToEvaluateOnNewDocument`
     — this needs to be confirmed at plan/execution time, not assumed (see Assumption A2).
   - Recommendation: the plan should include a small, explicit spike/verification step that
     confirms the chosen browser-automation tool can do pre-navigation script injection before
     committing to this as the FX-02 proof method; if it cannot, fall back to intercepting rAF
     via a `<script>` injected as early as possible post-load plus a documented caveat that the
     very first ~1-2 frames before injection are not covered.
