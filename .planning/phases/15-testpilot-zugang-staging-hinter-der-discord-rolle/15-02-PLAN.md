Lege `supabase/migrations/20260818001000_gate_verdict.sql` an mit genau einer
Funktion: `public.gate_verdict()`, `returns json`, `language plpgsql`,
`security definer`, `set search_path = public, auth`.

Sie nimmt KEINEN Parameter. Der Nutzer kommt aus `auth.uid()` — dieselbe Regel
wie in `verify-rsi`: die Identität stammt aus dem geprüften Token, niemals aus
einem Argument. Damit kann auch ein zufälliger Aufrufer nicht das Urteil über
ein fremdes Konto erfragen.

Ablauf, in dieser Reihenfolge:
1. `auth.uid()` ist `null` → `{"allowed": false, "grund": "keine-sitzung"}`.
2. Eine Zeile in `public.tester_blocklist` für diesen Nutzer →
   `{"allowed": false, "grund": "gesperrt"}`. Die Sperrliste kommt VOR allem
   anderen; sie ist der Sofort-Rauswurf aus D-10 und darf von keiner Rolle
   überstimmt werden, auch nicht von `admin`.
3. `public.user_roles.role = 'admin'` → erlaubt, `grund` `admin`. Das ist der
   Aussperr-Riegel aus D-04: er hängt an keiner Discord-Bedingung.
4. `public.discord_role_state.is_tester = true` → erlaubt, `grund` `tester`.
5. Sonst → `{"allowed": false, "grund": "kein-testpilot"}`.

Bei einem erlaubenden Urteil zusätzlich `last_staging_seen` fortschreiben:
`insert into public.discord_role_state (user_id, last_staging_seen) values
(v_uid, now()) on conflict (user_id) do update set last_staging_seen =
excluded.last_staging_seen`. Damit beantwortet D-13 („wann war er zuletzt auf
staging") sich aus dem Torvorgang selbst, ohne zweite Buchführung — und die
Übersicht in Plan 10 zeigt auch die, die die Rolle tragen und nie erscheinen.

Das erlaubende Urteil trägt außerdem `sub` (die Nutzer-ID) und `exp_hint` (300)
— `sub` wandert in die signierte Nutzlast des Ausweises, `exp_hint` hält die
Laufzeit an EINER Stelle statt in njs und SQL getrennt.

Die Rechte scharf stellen: `revoke all on function
public.gate_verdict() from public;` und `grant execute on function
public.gate_verdict() to authenticated;`. Die Rolle `anon` bekommt kein
Ausführungsrecht — ohne Sitzung gibt es nichts zu urteilen.

D-13, ebenfalls `security definer`, parameterlos, `set search_path = public,

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser/PostgREST → Postgres | Jeder angemeldete Client kann jede freigegebene Tabelle und Funktion aufrufen |
| Bot (Service-Rolle) → Postgres | umgeht RLS vollständig; alles, was der Bot schreibt, ist ungeprüft vertrauenswürdig |
| `security definer`-Funktionen → Postgres | laufen mit den Rechten des Eigentümers, nicht des Aufrufers |
